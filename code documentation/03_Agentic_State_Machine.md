# 3. Agentic State Machine (LangGraph)

## Overview
The heart of the knowledge extraction process resides in `src/agents/`. It uses **LangGraph** to model the extraction process as a highly robust, multi-agent State Machine. By decoupling planning, extraction, and validation into separate nodes, the system achieves a level of accuracy and domain-compliance impossible with a single LLM prompt.

## The State (`src/agents/state.py`)
All agents communicate by modifying a shared state object, defined as a `TypedDict` (`AgentState`). 
Key state variables include:
- `input_text`: The raw text to process.
- `domain`: The domain context (e.g., 'medical', 'legal').
- `planner_strategy`: The string generated by the Planner node detailing how to attack the text.
- `extracted_triples`: A list of Pydantic `Triple` objects (subject, predicate, object, confidence).
- `is_valid` & `validation_feedback`: Flags and text used by the Validator to govern retries.
- `iterations`: A counter to prevent infinite loops.

## Nodes (`src/agents/nodes.py`)
Each step in the graph is a discrete Python function that takes the `AgentState` and returns an updated dictionary of state values.

### 1. `planner_node`
**What it does:** Reads the input text and the domain configuration YAML (which specifies allowed entity types and predicates). It generates a bespoke extraction strategy.
**Why:** LLMs perform better when instructed to 'think step-by-step'. The planner breaks down complex domain constraints into a digestible strategy for the extractor.

### 2. `extractor_node`
**What it does:** Uses the strategy generated by the Planner to pull Triples from the text. 
**How it works:** It enforces strict JSON output and utilizes a custom parsing function, `robust_json_extract`. 
**Why `robust_json_extract`?** Open-weight models like Llama 3 and Mistral occasionally wrap JSON in markdown blocks, add conversational filler ("Here is your JSON..."), or break quotes. This function applies regex and fallback parsing strategies (including `ast.literal_eval` and replacing newlines) to guarantee that the agent graph does not crash due to malformed LLM responses.

### 3. `validator_node`
**What it does:** Acts as an automated supervisor. It looks at the `extracted_triples` and the original `input_text`. If the triples are hallucinated or violate domain rules, it generates feedback. If they are correct, it outputs 'PASSED'.
**Why:** It introduces a crucial feedback loop, vastly improving precision and reducing LLM hallucinations.

### 4. `deduplicator_node`
**What it does:** Takes the validated triples and normalizes the entity names (e.g., merging "Aspirin" and "aspirin 50mg" if semantically appropriate).
**Why:** To ensure a clean, dense Knowledge Graph where edges connect properly rather than creating thousands of disconnected, synonymous nodes.

## The Graph (`src/agents/graph.py`)
The `create_agentic_workflow()` function ties the nodes together using `StateGraph`. 
**The Routing Logic:**
- Start -> `planner` -> `extractor` -> `validator`
- At the `validator`, a **Conditional Edge** (`should_continue`) evaluates the state.
- If `is_valid` is `True` (or if it has retried 3 times), it routes to the `deduplicator` and then to the `END`.
- If `is_valid` is `False`, it routes back to the `extractor`, passing the `validation_feedback` to guide the LLM's next attempt.
